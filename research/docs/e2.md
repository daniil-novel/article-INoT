# E2 — абляции и adversarial-сценарии

**Связь со статьёй:** §7.3: E2a, E2b, E2c, E2d.

Эксперимент проверяет, какие компоненты Hybrid-INoT действительно вносят вклад
в качество, стоимость и устойчивость архитектуры.

## E2a — абляция компонентов

Сравнивается полный B3 Hybrid-INoT с тремя вариантами:

| вариант | что отключено | что проверяется |
|---|---|---|
| `B3a_no_compression` | сжатие контекста | вклад Algorithm 2 |
| `B3b_no_critic` | внутренний critic | нужен ли critic как отдельная роль |
| `B3c_no_self_check` | внешняя self-check проверка | нужен ли объективный verifier |

Каждая абляция сравнивается с полным B3 парным критерием Вилкоксона по
per-task `MAS_i`. Для среднего падения считается bootstrap CI 95%, а для
трёх сравнений применяется Holm-Bonferroni.

## E2b — систематическая ошибка critic

Процедура:

1. Найти задачи, на которых B0 ошибается.
2. Запустить B3 на этой подвыборке.
3. Посчитать, как часто critic выбирает кандидата, который затем не проходит
   внешнюю проверку.

Если частота выше 20%, это сигнал, что critic слишком часто уверенно выбирает
неверное решение.

## E2c — параллельные инструменты и граница H3

Используется Synthetic Tool-Use Suite: задачи имеют `k ∈ {2, 3, 4}` независимых
подзадачи и детерминированные задержки внешних инструментов.

Измеряются две вещи:

- latency LLM-оркестрации B2 против B3;
- прямой synthetic tool latency: serial Hybrid-style execution против
  parallel Classical-MAS-style execution.

Это важно для H3: если подзадачи действительно независимы, Classical-MAS может
параллелить tool calls, а последовательный внутренний цикл Hybrid-INoT теряет
преимущество по времени.

## E2d — чувствительность метрики

Архитектуры переупорядочиваются по `MAS_i` при изменении:

- весов `(w_cc, w_dup, w_warn, w_doc)` на ±20%;
- параметра `λ ∈ {0, 0.25, 0.5, 0.75, 1}`.

Если ranking часто меняется, значит итоговая метрика чувствительна к выбору
гиперпараметров.

## Как воспроизвести

```bash
python -m inot e2 --n 50 --seeds "42,123"
python -m inot view e2
```

## Артефакты

Результаты сохраняются в `results/e2/{e2a,e2b,e2c,e2d}/`.

- `runs.json`, `summary.json`;
- `pairwise_vs_full.json` для E2a;
- `tool_latency_serial.json`, `tool_latency_parallel.json` для E2c;
- `fig_ablation_mas.png`;
- `fig_latency_b2_vs_b3.png`;
- `summary.json` для E2d со всеми ranking-ами.

## Почему дизайн эксперимента корректен

- Все сравнения парные: одинаковые задачи и seed-ы.
- E2b специально выбирает сложные задачи, где critic наиболее важен.
- E2c использует задачи с истинной независимостью подзадач, а не эвристику.
- E2d меняет только веса и `λ`, поэтому проверяет устойчивость метрики, а не
  качество моделей.
