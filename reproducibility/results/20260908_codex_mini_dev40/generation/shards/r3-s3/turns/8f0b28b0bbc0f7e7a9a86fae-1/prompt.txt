Here is a stage-1 implementation plan for `task_func(url, directory, metadata)`.

## Goal
Upload **all files** from a given local directory to a server URL, attach the provided `metadata` to each upload, pause **1 second after each upload**, and return a **list of HTTP status codes**.

---

## Required behavior

### Inputs
- `url`: target server URL
- `directory`: path to a local directory containing files to upload
- `metadata`: extra data to send with each upload

### Output
- `list[int]`: status codes from each upload response, in file-processing order

### Exceptions
- Raise `FileNotFoundError` if `directory` does not exist
- Raise `TypeError` if `url` is invalid

---

## Implementation plan

### 1. Validate `url`
- Check that `url` is a valid URL-like string.
- Minimal validation should confirm:
  - it is a string
  - it is non-empty
  - it has a valid scheme/host structure, or at least starts with `http://` or `https://`
- If invalid, raise `TypeError`.

**Reasoning:** The prompt explicitly requires `TypeError` for an invalid URL.

---

### 2. Validate `directory`
- Use `os.path.exists(directory)` and/or `os.path.isdir(directory)` to confirm the directory exists.
- If not, raise `FileNotFoundError`.

**Reasoning:** The function must fail early if the directory is missing.

---

### 3. Collect files in the directory
- List entries in the directory with `os.listdir(directory)`.
- Filter to include only regular files, not subdirectories.
- Use a deterministic order, preferably sorted alphabetically, so status codes are returned consistently.

**Reasoning:** “All files” should not include nested folders unless explicitly intended, and sorted order makes behavior predictable.

---

### 4. Prepare upload payload for each file
For each file:
- Build its full path with `os.path.join(directory, filename)`
- Open it in binary mode
- Attach:
  - the file itself
  - the metadata

### Metadata handling
Because the prompt says “along with the associated metadata,” the plan should define a consistent transport format. Two common options are:

1. **Multipart upload**:
   - file sent as binary upload
   - metadata sent as JSON string in a form field

2. **JSON payload**:
   - file content encoded into text/base64 and combined with metadata in JSON

Given the presence of `requests` and the likely expectation of file upload, multipart is usually the most practical approach.

---

### 5. Send the request
- Use `requests.post(url, ...)` for each file.
- Capture `response.status_code`.
- Append the status code to the result list.

### Error handling during upload
- The prompt does not specify network exception handling.
- A practical implementation should decide whether to:
  - let `requests` exceptions propagate, or
  - catch them and continue per file

Since the output must be a list of status codes, the cleanest interpretation is:
- let unexpected request errors propagate unless otherwise specified

---

### 6. Apply speed limit
- After each upload attempt, call `time.sleep(1)`.

**Important detail:**  
The pause should happen **after each upload**, whether the upload succeeds or fails, unless the function is intentionally designed to stop on exceptions.

---

### 7. Return result
- Return the list of collected HTTP status codes.

---

## Edge cases to consider

### Directory-related
- Directory exists but is empty → return `[]`
- Directory path points to a file, not a directory → treat as invalid directory, likely `FileNotFoundError`
- Directory contains subdirectories → skip them, upload only files
- Directory contains hidden files → include them if they are regular files unless excluded explicitly

### URL-related
- URL is `None` → `TypeError`
- URL is not a string → `TypeError`
- URL is an empty string → `TypeError`
- URL missing scheme or malformed → `TypeError`

### Metadata-related
- `metadata` is `None` → should still be sent or converted consistently
- `metadata` is not JSON-serializable → if using JSON serialization, this can fail
- metadata is large or nested → ensure serialization is safe and consistent

### File-related
- File cannot be opened due to permissions → should raise the corresponding I/O exception
- Directory contains non-UTF8 filenames → handle paths via `os` and let `requests`/Python manage encoding as needed
- Very large files → binary streaming may be preferable to reading entire file into memory

### Network / server-related
- Server returns non-2xx codes → still append those codes to the list
- Server unavailable → request may raise an exception
- Partial failure across files → decide whether to stop immediately or continue; the prompt does not require recovery logic, so simplest is to propagate exceptions unless specified otherwise

### Rate limiting behavior
- Ensure `time.sleep(1)` is called after each file upload
- If no files exist, no sleeping should occur
